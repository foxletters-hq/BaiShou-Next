# 统一整理实施计划

> **状态**：第一批至第五批已落地
> **范围**：`packages/core`（`graph`、`knowledge`、`raw-data`）、`packages/database`、`packages/shared`、`apps/desktop`、`apps/mobile`
> **数据影响**：第一批与第二批只加列、不迁移数据、不改 JSONL 记录类型、不改同步协议；第三批改节点 ID 公式、唯一索引与 JSONL 记录类型，需要迁移
> **本计划定义「整理」这一个动作的顺序与实体身份规则**，不合并全局关系图与笔记本关系图

---

## 1. 要解决的问题

### 1.1 两套图的向量不对称

全局关系图的节点有向量。`graph_nodes` 上有 `embedding`、`dimension`、`model_id`，抽取时可以用向量召回候选节点，`GraphRepository.searchNodesByVector` 支持语义搜索。

笔记本关系图的节点没有向量。`notebook_graph_nodes` 上没有这三列，`NotebookGraphRepository.searchNodes` 只做 `name` 的 LIKE 匹配、`name_normalized` 的等值匹配和别名表匹配。`KnowledgeGraphExtractionService` 合并实体只靠 `findNodeByName`，既不算向量也不做二次判定。

结果是同一个人在两份资料里写成「张三」和「小张」时，笔记本图永远是两个节点。

### 1.2 整理顺序两边不一致

日记这条线要求先向量后抽图，但抽图要用户另外触发：`GraphLlmExtractionService.extractDiaries` 先调 `assertEmbeddingConfigured`，再对每篇调 `assertDiaryEmbedded`，未向量化的报 `GRAPH_EXTRACT_DIARY_NOT_EMBEDDED`。向量完成后不会自动接着抽图。

知识库这条线没有这个顺序。`KnowledgeIngestService` 抽出正文后同时排 `embed` 与 `graph` 两个任务，消费端把它们分在两条车道上（`INDEX_STAGES` 与 `GRAPH_STAGES`），谁先完成不确定。图可能在分块向量还没写完时就抽完。

### 1.3 同一个节点的向量被算两次

`alignEntityPool` 对名字没命中的实体用 `${name}\n${summary}` 算向量，用来召回候选，**算完不落库**。同一个节点的向量后来由 `GraphSyncService`（同步入库时发现缺同模型向量）或 `backfillUnembeddedGraphNodes`（手动补齐）再算一次才写进 `graph_nodes.embedding`。

### 1.4 同名不同人存不下

节点 ID 是名字的哈希：`graphNodeIdForEntity` 取 `md5(vaultId \0 nodeType \0 normalizeGraphName(name))`，笔记本版本再加 `notebookId`。表上还有部分唯一索引 `graph_nodes_vault_type_name_live`（`vaultId, nodeType, nameNormalized`，条件为未删除且非 `entry`），笔记本侧对应 `idx_nb_graph_nodes_live_name`。

所以归一化同名在当前结构里就是同一个实体，一个人的父亲和同事同名时无法分开存放。手工建节点或改名撞上同名会被直接拦住，返回 `{ conflict: 'same-name' }`，界面提示用户换名或合并过去。

## 2. 「整理」的定义

整理是一个动作，一条顺序，日记、伙伴记忆、知识库资料共用。

| 阶段             | 做什么                                           | 谁需要         |
| ---------------- | ------------------------------------------------ | -------------- |
| 1 抽正文         | 从文件里取出可读文本                             | 只有知识库资料 |
| 2 原文向量       | 日记正文、伙伴记忆、资料分块写入各自向量表       | 全部           |
| 3 抽图           | 抽实体与带类型的边，做实体对齐                   | 全部           |
| 4 节点向量与消歧 | 本批新节点落库向量；歧义名走判定；可疑节点进复核 | 全部           |

阶段 3 必须等阶段 2 完成，这是两边统一的门槛。阶段 4 里本批新节点的向量在阶段 3 对齐时已经算出，直接落库，不再重算。

## 3. 已锁定的决策

以下为已确认的决策，后续复查不得再当作缺口。

| 项           | 决定                                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------------------------ |
| 存储         | 两套图各自存表，不合并。资料分块向量与节点向量是两类对象，各写一次                                           |
| 顺序         | 原文向量 → 抽图 → 节点向量，两边一致。未完成原文向量不准抽图                                                 |
| 入口         | 常规整理收拢成一个动作，知识库与日记共用同一条进度；单资料重抽与整本重建作为维护动作保留，同样遵守顺序门槛   |
| 向量落库时机 | 抽取对齐时算出的向量直接落库；集中补齐只负责中断、失败与升级前的空位                                         |
| 节点嵌入文本 | 保留 `${name}\n${summary}`。向量随信息累积偏移是消歧依据，不改成只用名字                                     |
| 重算条件     | 保留名或摘要变了才重算；只新增别名且名片文本未变则保留旧向量                                                 |
| 节点 ID      | 保留内容派生的确定性 ID，不改随机 ID                                                                         |
| 消歧位置     | 新增 `discriminator` 列，默认空字符串，参与 ID 哈希与唯一索引；`name` 仍为「张三」，区分信息在界面上单独显示 |
| 裸名归属     | 第一个实体的 `discriminator` 为空，ID 与现在完全一致，老数据零迁移；第二个同名实体才带区分信息               |
| 区分信息来源 | 只能由用户确认的拆分动作产生并登记；抽取只能从已登记候选中选择，不许新造                                     |
| 判定失败     | 模型判不出或报错时不自动新建第二个实体，标记为待用户确认                                                     |
| 相似度门槛   | 0.5 仍然只是召回门槛，不是自动合并线。是否合并由二次模型判定，向量近不构成硬合并                             |

### 为什么保留确定性 ID

确定性 ID 承担跨设备去重。两台设备各自抽到同一个名字，算出的 ID 相同，同步时 `foldJsonlRecordsById` 按 ID 折叠成一条，同 ID 取 `updatedAt` 大的，不需要任何协商。

换成随机 ID 之后，这个免费去重会消失，而且不是以「冲突」的形式暴露。图分片是按文件分的（全局图按月，笔记本图按资料），两台设备写不同分片时根本不产生冲突，`shouldLineMergeMonthlyJsonlOnConflict` 只对伙伴记忆分片做行级合并、图分片整文件覆盖这条规则也不会被触发。两条不同 ID 的记录会分别留在两个互不冲突的文件里长期共存。

另外抽取是增量的，设备读到 extract-state 与内容哈希后会跳过已抽过的条目，不存在「某台设备每次都从零重抽出一套干净的表」这个前提。

## 4. 分批实施

### 第一批：去掉重复处理，补齐笔记本图向量

不碰节点 ID、唯一索引与同步协议。

**知识库改成串行。** `KnowledgeIngestService` 抽出正文后不再同时排 `embed` 与 `graph`，改为 `embed` 完成后再排 `graph`；消费端两条车道（`INDEX_STAGES` 与 `GRAPH_STAGES`）的划分随之调整。

排 `graph` 阶段的入队点共五处，串行化要全部覆盖，不能只改 `processExtractJob`：

| 入队点                     | 性质                       | 改法                                     |
| -------------------------- | -------------------------- | ---------------------------------------- |
| `processExtractJob`        | 抽完正文后的常规路径       | 改为 `embed` 完成后再排                  |
| `retrySource`              | 重试失败资料               | 同上                                     |
| 笔记本批量重处理           | 整本资料重排               | 同上                                     |
| `reprocessSource('graph')` | 维护动作：重抽单份资料的图 | 保留入口，执行前校验该资料已完成分块向量 |
| `rebuildNotebookGraph`     | 维护动作：重建整本图       | 同上                                     |

后两处是有价值的维护动作，不在「收拢入口」的删除范围内，只是要加上顺序门槛。

**日记抽图接到向量之后。** 原文向量完成后自动进入抽图阶段，不再要求用户另外触发。现有两个门槛错误码保持不变。

**对齐时的向量直接落库。** `alignEntityPool` 把算出的向量交还给调用方，`commitDrafts` 在写节点时一并写入 `embedding` 与 `model_id`；`GraphSyncService` 与 `backfillUnembeddedGraphNodes` 遇到已有同模型同维度向量时继续跳过，不重复调用嵌入接口。

**笔记本图节点加向量。** `notebook_graph_nodes` 增加 `embedding`、`dimension`、`model_id` 三列，走 `knowledge-schema.shared.ts` 里的 `ADD COLUMN` 补列；仓储补 `updateNodeEmbedding`、`listUnembeddedLiveNodes`、`searchNodesByVector`、`clearNodeEmbedding`；`KnowledgeGraphExtractionService` 接入 `alignEntityPool`，复用名字命中、向量召回、二次模型判定这一套，不再只按名字合并。

节点向量**不进 JSONL**。`GraphNodeRawRecord` 与 `NotebookGraphNodeRawRecord` 都没有向量字段，向量只存本机 SQLite、不参与同步，各设备各自生成。因此这一批不改任何 raw 记录类型，也不动同步协议。

**待嵌入计数纳入笔记本节点。** `PendingEmbedCounts` 与相关文案说明包含笔记本图节点，与「知识库资料」这一项区分开。

测试：知识库任务顺序、对齐向量落库后不再重复调用嵌入接口、笔记本图向量召回与二次判定、待嵌入计数。

### 第二批：统一整理外壳

**抽图成为分阶段流水的一个阶段。** `runManualPendingEmbedFill` 现有阶段为日记、伙伴记忆、图节点、知识库，新增抽图阶段并保持顺序语义；`RagBatchEmbedPhaseCounts` 与进度文案随之扩展。

**入口与进度收拢。** 知识库与日记共用一个整理入口与一条进度，中断后可从停下的阶段继续。

测试：阶段顺序与计数推进、中断后续跑、空数据与单条数据。

### 第三批：同名消歧的身份层

本批只打通身份层与用户手工拆分，不做自动扫描与自动判定，后者留到第四批。

**先记一条实情：同名现在不是「选择了合并」，而是机械上存不下。** 有两道卡点，二次模型完全插不上手。第一道在 `alignEntityPool` 的第一步：名字与别名等值命中就直接复用并 `mergedBy: 'name'`，所以第二个「张三」压根进不了 `judgeMerges`，二次模型只对「张三」与「小张」这种名字不同的称呼起作用。第二道在 ID：即使绕过第一步、让模型判出不是同一个人，`assignCreate` 走的仍是 `nodeIdForEntity(type, name)`，算出来和已有节点逐字相同，写下去还是折叠成同一条，后面还有部分唯一索引兜着。所以要改的是身份，不是判定策略。

**加消歧列。** `graph_nodes` 与 `notebook_graph_nodes` 增加 `discriminator`，默认空字符串；`graphNodeIdForEntity` 与 `notebookGraphNodeIdForEntity` 的哈希输入加入这一段；两个部分唯一索引（`graph_nodes_vault_type_name_live` 与 `idx_nb_graph_nodes_live_name`）加入这一列并重建。

**区分信息为空时哈希输入必须逐字不变。** 现在是 `md5(${v}\0${t}\0${n})`。只有区分信息非空时才追加 `\0${d}`，为空时连分隔符都不许多加，否则全部老节点的 ID 会集体改变。这一条必须有一个断言旧值的测试守住。

**唯一索引要先删再建。** `GRAPH_INDEXES_SQL` 与 `NOTEBOOK_GRAPH_INDEXES_SQL` 用的是 `CREATE UNIQUE INDEX IF NOT EXISTS`，已存在的索引不会被改写。加列后必须先 `DROP INDEX IF EXISTS` 再按新列建，且在全新库上同样安全。

与第一批不同，`GraphNodeRawRecord` 与 `NotebookGraphNodeRawRecord` 这次**必须**扩展：区分信息参与身份，必须跨设备一致，JSONL 是真源。

**不能借用 `name_normalized` 这一列。** 它是 `name` 的纯派生，`NotebookGraphRepository` 的四处写入与 `GraphRepository` 的两处写入都会在落库时用 `normalizeGraphName(row.name)` 重算它，ID 哈希也不读这一列而是直接调 `normalizeGraphName(name)`。把区分信息塞进去会被这些地方静默覆盖，必须新增独立列。

**两个库的补列机制不同。** Agent 库走 `agent-schema-compat.ts` 的声明式列清单（缺列时执行声明的 `ddl`），知识库走 `knowledge-schema.shared.ts` 里的命令式 `ADD COLUMN`。两侧要分别加。

**`findNodeByNameOrAlias` 的返回从单条变多条，这是一次跨文件签名变更。** 涉及 `graph.ports.ts`、`graph.repository.ts`、`graph-llm-extraction.service.ts`、`find-or-create-graph-node.ts`、`graph.ipc.ts`、`AgentChatService.ts`、`mobile-graph.service.ts`、`start-agent-chat.ts` 及对应测试。调用方要分成「只关心是否存在同名」（同名冲突拦截）与「需要在多个候选中挑选」（抽取对齐）两类分别处理。

改多返回不是为了将来好扩展，是拆分之后立刻就需要：裸名会同时是第一个实体的 `name` 和第二个实体的别名（`find-or-create-graph-node.ts` 的 `forceId` 路径会把传入名字并进别名），而 `graph_node_aliases_vault_alias` 不是唯一索引，两个节点都带「张三」这个别名时单条返回是不确定的。

**拆分登记存裸名节点的 `props_json`。** 与现有 `mergeHistory` 的存法一致，不引入新的分片种类与同步路径。登记内容是「这个名字在本库里对应哪几个实体」：每条含区分信息、节点 ID、展示标签、登记时间。已知限制：裸名节点被删除时登记随之消失；两台设备同时登记同一个名字时按最后写入收敛。若要避免这两点，需要新增独立的登记分片并接入同步路径，代价更大，本批不采用。

**抽取遇到多候选时本批不判定。** 名字查到零条或一条，行为与现在完全一致，直接复用，零额外成本。查到多条时不新建节点、不猜归属：边照常挂到裸名节点，但 `reviewStatus` 写 `pending`，同时把这条出处记进裸名节点的受影响出处清单，用户在现成的节点与边复核列表里改挂。这样既不静默归错人，也不引入新的模型调用；量也可控，只在用户主动拆分过的名字上发生。受影响出处清单同时满足风险一节里「复核要能列出登记变化后写入过的出处」这条要求。

**手工拆分。** 入口只有一个：用户在节点详情页发起。新增 `packages/core/src/graph/graph-split-node.ts`，负责写登记、用带区分信息的 ID 建第二个节点、按用户分配改挂历史边。改挂边的部分复用 `mergeDiaryGraphNodes` 已有的边重写机制。必须可重入：中途报错或被强制关闭后重新打开拆分界面，要能看出哪些边还没分配，已改挂的不再重复处理。

**撤回拆分。** 反向合并直接复用 `mergeDiaryGraphNodes`，保留裸名一方、拆出的一方软删除、边改挂回去。撤回时必须同时删掉登记，否则下次抽取还会看到那个候选，用户会认为撤回没生效。

**界面（本批只做桌面端）。** 节点主体仍显示 `name`，区分信息作为标签或副标题显示；新增拆分确认界面；手工建节点撞同名时的提示从「请先换名」扩展为可以选择登记为另一个实体。移动端本批只跟签名变更并显示区分信息，不做拆分入口。

**已知不保证：旧版本设备写回时会丢区分信息。** raw 记录是普通 TS 接口，没有严格校验，旧版本读到多出来的字段会忽略，不报错。但旧版本一旦动了这个节点——改摘要、改名、参与合并——它会按自己认识的字段重拼一条记录写回，区分信息被删掉，该记录的 ID 与内容从此对不上。本批接受这个限制，不做旧版本兼容处理。

测试：区分信息为空时 ID 与旧值逐字相同、带区分信息时 ID 与唯一索引的行为、登记的读写与撤回后清除、名字查到多条时的分支、抽取遇多候选时边标 `pending` 且出处入清单、拆分后边的归属、拆分中断后重入。

### 第四批：自动检测与自动判定

**整理阶段扫描可疑节点。** 扫描同一节点同时挂上互斥类型的关系、出处横跨明显不同的时间段与场景这类信号，交模型给出怀疑理由，由用户确认是否拆分以及历史边如何归属。第三批只在节点详情页被动提示，本批才接进整理流水，届时要一并看几万节点下的扫描成本。

**抽取多候选时交模型判定。** 把候选与本篇上下文交给模型，只允许从候选中选一个；模型判不出或报错时维持第三批的行为（挂裸名 + 边标 `pending`），不自动新建。

**笔记本图的跨窗口对齐。** 笔记本图目前按窗口逐个落盘，上一个窗口刚写出、还没进 SQLite 的节点，下一个窗口的向量召回看不到，只能靠内存里的名字表兜住，所以跨窗口的同人异名识别不了。全局关系图是整批对齐后再写，没有这个问题。本批把笔记本图改成「先抽完全部窗口，再整批对齐一次再写」，与全局图统一。这会改动当前按窗口落盘的检查点语义，中断续跑的行为要一并调整。

**移动端拆分入口。** 与桌面端对齐。

测试：可疑节点扫描的命中与误报、抽取多候选时的选择与失败路径、笔记本图整批对齐后中断续跑、两端拆分行为一致。

**本批落地说明（不改锁定决策）。** 同名多候选时可选 `judgeNameCandidates`：只允许返回已有候选 id，失败则维持第三批的裸名 + `ambiguous`。笔记本图改为先抽完全部窗口并写入 `extractedWindows`，再整批 `alignEntityPool` 一次；`alignWritten` 为真才算抽图完成。整理流水在 `graph_extract` 之后增加 `graph_disambiguate`：纯函数收集信号，最多 40 次模型调用写 `props.suspectReason` 与 `reviewStatus=pending`，不自动拆分。`graph:list-suspect-nodes` 列出待审且带怀疑理由的节点。移动端拆分入口与桌面端对齐：节点详情可拆分/撤回，新建撞同名时可登记为另一个实体。

### 第五批：整理顺序对齐与相似待合并

本批不改第 3 节锁定决策。补齐两端整理顺序、吃不准时的人工入口，以及笔记本图同步改名片后的向量。

**整理顺序。** 共享阶段固定为日记 → 伙伴记忆 → 知识库 → 抽图 → 节点向量 → 可疑扫描。原文向量完成后再入抽图队列；知识库 INDEX 车道只消费 extract/embed，GRAPH 车道只消费 graph，同一份资料先嵌入再抽图。手机日记待办为 0 仍跑后续 fill；空图「开始整理」走统一 `batchEmbed`。

**改名片重算向量。** 人生图 `GraphSyncService` 用 `shouldReuseGraphNodeEmbed`：同模型且 `${name}\n${summary}` 没变才跳过。笔记本图抽图覆盖走 `refreshNotebookEmbeddingsAfterAlign`。笔记本图 pending-index 用 `shouldRefreshExistingGraphNodeEmbed`：库里已有同模型向量且名片变了才重算；新节点仍留给抽图落库或集中补齐，避免同步灌库时把整本再嵌一遍。抽图路径不把嵌入器传给 `NotebookGraphIndexService`，避免和 `writeAlignedEmbeddings` 算两次。

**高准确合并。** 相似度 > 50% 仍交给二次判定，并带上裁剪后的日记片段。模型吃不准时新建第二个节点，在 JSONL `props` 写 `similarPending`，不改 `reviewStatus`。同 peer 后写覆盖先写。不建详细出处登记。

**相似待合并页。** 两端关系图各加一页，只列相似待合并对；合并保留已有节点，不是同一人则去掉这对标记。可疑扫描理由仍写在节点详情。

**查找与改挂。** `findNodesByNameOrAlias` 为规范查询；手机 mutate 用它加 `pickSameNameConflictFromHits`。合并与拆分的改挂边抽到 `remapTouchingEdges`。

**知识维护。** 手机补重试、只重抽图、重建整本图；重建索引仍先 embed，正文已抽出的资料标记 embed 后再入 graph。不做 workbench。

测试：阶段顺序、日记为 0 仍 fill、reuseEmbed / 笔记本改名片重算、judgeMerges 带出处与 uncertain、list/dismiss 对、两端 similar 页签、改挂边、同名多查、last-batch-wins。

## 5. 明确不做

1. **不合并两套图。** 全局关系图与笔记本关系图保持隔离，跨库同名实体不合并。
2. **不把笔记本节点写进全局关系图。** 资料与会议里的人不进入人生关系图。
3. **不拿资料分块向量当节点向量。** 分块向量只服务资料检索。
4. **不引入外部自然语言处理运行时做实体识别。** 技术栈不匹配，中文称谓与昵称识别效果不足，而且本项目需要带类型的边而非实体清单。
5. **不放弃带类型的边。** 关系图要展示给用户，边的类型有独立的产品价值。
6. **不改成向量近即合并。** 是否合并始终由二次模型判定。
7. **不把区分信息拼进 `name`。** 理由见下节。
8. **不让抽取自由生成区分信息。** 理由见下节。

### 为什么不把区分信息拼进名字

`name` 是展示名，拼成「张三-某公司同事」会让节点标签变长且与其他节点不对称。别名表的 `(vaultId, aliasNormalized)` 索引不是唯一索引，两个节点都带「张三」这个别名时 `findNodeByNameOrAlias` 的返回是不确定的。名字精确命中这条零成本快路也会失效，只能改成前缀模糊匹配。

### 为什么不让抽取自由生成区分信息

区分信息参与 ID 哈希。若由模型每次即时生成，同一个实体在不同设备、不同批次上会得到不同的字符串，归一化后算出不同的 ID，跨设备去重会不可预测地失效，比改随机 ID 更难排查。因此新的区分信息只能由低频、有用户参与、有登记的拆分动作产生。

### 区分信息定了就不改

区分信息参与 ID，改动它等于换 ID 并改挂全部边、重算向量、重写 JSONL。它是身份标记，不是描述。实体的现状变化写在摘要里，不通过改区分信息表达。

## 6. 风险与牵连

**第三批改 ID 公式牵连同步逻辑。** `shouldKeepIncomingGraphNodeId` 与 `shouldKeepIncomingNotebookGraphNodeId` 的偏好判断、`applyRawNode` 撞唯一索引时的重映射处理都要跟着改。

**唯一索引改动需要迁移。** 两个索引都是 SQLite 的部分唯一索引，加列后要重建。

**移动端在范围内。** 整理入口、待嵌入计数、图页面与知识库详情页移动端都有对应实现，第一批与第二批会碰到。

**拆分比合并难。** 合并只需保留一方，拆分要重新分配历史边，分错的后果比不分更糟，因此必须由用户确认，不允许模型直接落盘。

**登记尚未同步到位时会归错人。** 设备 B 还没收到拆分登记就重抽同一篇日记，它看不到候选，会按裸名写入，算出的是裸名 ID。结果是这一篇的关系挂到了第一个实体上，属于**归错人，不是多出一个节点**——裸名 ID 是确定的，不会产生重复。纠正方式是登记同步到位后，在下次整理的拆分复核里重新判定受影响的出处。实现时要让复核能列出「登记变化后写入过的出处」，否则用户无从发现。

**移动端抽取入口同样要接门槛。** `resolveMobileGraphExtractAlignDeps` 与 `mobile-graph-extract-queue.service.ts` 已经在调用前校验嵌入配置，第三批的多候选判定与登记读取要在移动端一并接上，否则两端行为会分叉。

**热门节点召回待观察。** 高频实体会被大量关系牵连，当前没有按关联数量降权的机制。本计划不改打分，但第二批上线后应观察召回质量，必要时另立范围处理。
