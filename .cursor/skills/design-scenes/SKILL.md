# 设计场景

用户难以确定一个设计时，**先从实际使用方式出发，再讨论实现机制**。通过多个场景进行比较，不要在方案尚未明确前直接编写实现或预先认定某种方案。

不要用 `todo-review`（核查计划是否落实）或 `/code-review`（检查本次变更是否存在问题）代替。本流程关注的是：在不同使用者和使用过程中，这个设计会产生什么结果。

## 执行步骤

```
场景分析：
- [ ] 1. 用一句话说明方案要改善什么、需要放弃什么
- [ ] 2. 先描述一个能够体现方案合理性的典型场景
- [ ] 3. 分析 3～5 个可能暴露问题的场景（不要只举一个反例）
- [ ] 4. 对每个问题场景，说明当前方案和对照方案分别会发生什么
- [ ] 5. 说明方案实际上优先支持哪一类使用方式，然后等待用户选择
```

用户没要求落地时，不要改代码、不要开计划文件。

## 1. 一句话概括产品取舍

先复述方案，让用户可以纠正理解：

- 这套设计让哪一种使用方式更简单
- 它默认不经常发生的是哪一种使用方式

如果无法说明这种取舍 → 先提问，不要开始场景分析。

## 2. 典型场景（说明方案为什么合理）

写一个简短场景：可以涉及一个人、一台设备，或更换设备后只下载数据。使用具体对象（某个月的账本、某个人名、删除或新增操作），不要以协议名称开头。

如果连典型场景都无法说明清楚，先暂停分析，因为方案本身还不完整。

## 3. 场景比较

至少覆盖下面适用的场景类别（如果跳过某类，应说明原因）：

- 两个人或两台设备**同时修改同一份数据**
- 一台设备长时间离线后重新连接
- 数据只完成部分传输、处理或显示
- 撤销操作、删除后重新创建、内容相同但名称不同
- 数据为空、只有一个使用者、从不进行同步（确认「简单情况」仍然成立）

每个场景控制在四行以内，说明参与者、执行的操作以及另一端看到的结果。不要一开始就列出优缺点表。

对照方案只在可能暴露问题的场景中出现，用于比较结果，不要一开始就评选方案。

## 4. 收束

用三到五行说明：当前需要决定的不是实现细节，而是**接受哪些使用场景、不保证哪些使用场景**。列出用户可以选择的产品取舍（例如「同时只使用一台设备编辑」或「允许多台设备编辑同一份数据」）。

然后暂停，等待用户选择。用户确定取舍后，再讨论如何简化实现机制；用户未确定前，不要建议开始实施。

## 输出

使用中文。以场景分析为主要内容，以实现机制作为补充说明。聊天中不要直接使用大型对比表；如果用户要求简单对比，应在场景分析之后用不超过四行进行说明。

禁止：

- 用协议名当第一节标题
- 把「更正确」当成无需场景的结论
- 代码或回复里写其他产品名
- 将场景分析扩展为架构长文（单个场景超过一屏时应当缩短）

场景清单和反例见 [reference.md](reference.md)。
