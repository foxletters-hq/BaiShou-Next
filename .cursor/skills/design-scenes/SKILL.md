# 设计场景

一个设计还没定下来的时候，先说清楚**人在什么情况下会怎么用、会看到什么结果**，再讨论代码怎么写。

这个技能要解决的是一种常见的失败：方案在纸面上讲得通，但一旦放进真实使用过程，就会出现「用户以为删掉了其实还在」「换了台设备就搜不到了」「数据一多就卡住」这类问题。这些问题靠盯着代码看不出来，必须把使用过程一段一段还原出来。

不要用它代替 `todo-review`（核查计划有没有落地）或 `/code-review`（检查这次改动有没有问题）。

---

## 三条硬要求

1. **说完整、规范的中文。** 可以用技术名词，但要把动作写明白。该说「删除 / 保留 / 覆盖 / 合并 / 比较 / 重新生成」就直接写这几个词，不要用需要对方猜的说法。
2. **场景里必须有人、有具体东西、有结果。** 「两台设备并发时最后写入者优先」不是场景。「用户在电脑上删掉了张三这条记忆，手机当时没联网，第二天手机连上以后看到张三又回来了」才是场景。
3. **结尾必须用 `AskQuestion` 工具提问。** 分析完要提炼成 2 到 4 个具体方案，让用户点选，不要在正文里用「方案一、方案二」列清单让用户打字回答。

---

## 执行步骤

```
- [ ] 1. 说清这次设计想让什么变简单，代价是什么
- [ ] 2. 讲一个典型场景，说明方案正常工作时是什么样
- [ ] 3. 从场景库里挑 3 到 5 个真正相关的维度，说明跳过了哪些维度以及为什么
- [ ] 4. 对每个可能出问题的场景，说明当前方案和对照方案分别会发生什么
- [ ] 5. 提炼成 2 到 4 个方案，调用 AskQuestion 让用户选择
```

用户没有明确说要落地之前，不改业务代码、不建实施计划文件。

---

## 1. 先说清取舍

用两三句话复述你理解的方案，让用户能当场纠正：

- 这套做法让哪一种使用方式变顺畅
- 它默认哪一种情况不常发生，因此暂时不优先保证

如果连这个取舍都说不出来，说明方案本身还缺信息。**先提问，不要硬着头皮开始分析。**

## 2. 典型场景

举一个贴近日常的例子，说明方案正常工作时的样子。要具体到人做了什么动作、隔了多久、在哪台设备上看到什么。

好的开头：

> 用户晚上在电脑上写完当天的日记，第二天在地铁上打开手机，手机自动补上了检索索引，搜「上周和李四聊的那件事」能搜到。

不好的开头：

> 同步层采用最后写入优先策略，保证最终一致性。

典型场景都讲不清楚，就先停下来问用户，不要接着推演。

## 3. 挑场景，不要每次都挑同一组

从下面的场景库里挑 **3 到 5 个真正跟这个设计相关的维度**，并说明你跳过了哪些、为什么跳过。同步类设计容易一路只讲多设备冲突，那样会漏掉数据量、误操作、认知落差这些更常见的问题。

| 维度         | 要问的问题                                                                     |
| ------------ | ------------------------------------------------------------------------------ |
| 时间与积累   | 用了一天和用了三年，表现有区别吗？数据从几十条长到几万条会怎样                 |
| 人与角色     | 第一次打开的新用户看到什么？从旧版本升级上来的老用户呢                         |
| 设备与并发   | 两台设备同时改同一份数据会怎样？一台离线很久再连上会怎样                       |
| 中断与失败   | 断网、报错、进程被强制关闭、磁盘写满、权限被拒绝，分别停在哪一步，下次怎么接上 |
| 误操作与后悔 | 删错了能不能找回？同一个动作点了两次会怎样                                     |
| 认知落差     | 用户以为发生了什么，实际发生了什么？两者不一致时他会怎么理解                   |
| 规模与等待   | 要等多久？会不会卡住界面？后台跑起来会不会打断正在做的事                       |
| 外部干预     | 用户直接改了文件、用别的工具动了这个目录、把文件挪走了，会怎样                 |
| 升级与回退   | 旧格式数据怎么处理？新旧版本轮流用同一份数据会怎样                             |
| 平台差异     | 桌面和移动端在权限、后台执行、存储位置上的差别会不会导致行为不一致             |
| 空与极简     | 完全没有数据、只有一条数据、从不同步的用户，这套机制还成立吗                   |
| 可见性       | 哪些内容会离开这台设备？用户看得到吗？想撤回时能撤回吗                         |

每个场景控制在四行以内：谁、在什么设备上、做了什么、另一边看到什么。

## 4. 引入对照方案

对照方案只在可能出问题的场景里出现，用来比较结果，不要一上来就评优劣。同一个场景下写清楚：当前方案会怎样、对照方案会怎样、差别对用户意味着什么。

避免把技术差异直接抛给用户。「只在本机比对」和「把完成状态一起同步」这种区别，要翻译成「换新设备后要等一次重新生成」和「换新设备可能什么都搜不到」这样的实际体验。

## 5. 收束并提问

用三到五行说明：现在要定的不是实现细节，而是**接受哪些使用情况、暂时不保证哪些使用情况**。

然后调用 `AskQuestion`，给出 2 到 4 个方案选项。每个选项要写清这个方案带来什么、放弃什么；把你推荐的放第一个并标注「推荐」。

用户选完之后再讨论怎么实现。用户没选之前，不要建议开始动手。

---

## 输出规范

- 全程中文，把动作写明确。
- 场景分析是主体，实现机制是补充。
- 聊天里不要一上来就摆大对比表；用户要简单对比时，在场景分析之后用不超过四行说明。
- 不提任何其他项目的名称。

## 禁止

- 用协议名或机制名当小节标题。
- 把「这样更正确」当成不需要场景支撑的结论。
- 单个场景写到超过一屏。
- 结尾不提问，或者在正文里列选项让用户自己打字选。
