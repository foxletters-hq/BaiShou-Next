# 设计场景：场景分析方法

## 与审查类技能的区别

| | 设计场景 | 待办审查 | `/code-review` |
|---|---|---|---|
| 问的是 | 这种使用方式下会发生什么 | 当前结论是否成立 | 本次变更是否存在问题 |
| 输入 | 难以确定的设计 + 对照方案 | 计划 / 待办事项 | 变更差异 |
| 输出 | 典型场景 + 问题场景 + 产品取舍 | Canvas 断言表 | Findings |

## 场景分析时优先确认的问题

- 谁在编辑数据？是一台设备，还是两台设备会修改同一份数据
- 另一台设备当前是否在线，所持有的数据是否过期
- 删除和新增是否会作用于同一个文件、同一天或同一个月份
- 数据确实不存在，还是当前尚未读取到
- 用户认为自己正在撤销操作时，系统是否可能将其理解为另一台设备的覆盖操作

## 典型场景 / 不合适的分析开头

- 合适：电脑修改李四的记录，手机删除张三的记录，两端都上传八月账本
- 合适：手机一周未连接，电脑每天修改数据，手机恢复连接后先上传旧账本
- 不合适：只说“并发时最后写入者优先更正确”，没有具体参与者和操作
- 不合适：只说“追加日志中的删除标记有意义”，没有具体使用场景，机制成了主要内容

## 总结句式

「你现在需要的是：让____这种使用方式更简单；代价是暂不保证____这种使用方式。选择前者时，实现可以简化为____；选择后者时，必须保留____。」
