# 设计场景：场景库与写法参考

## 和其他审查类技能的区别

|            | 设计场景                         | 待办审查                 | `/code-review`         |
| ---------- | -------------------------------- | ------------------------ | ---------------------- |
| 回答的问题 | 真实用起来会发生什么             | 之前定的结论现在还成立吗 | 这次改动有没有引入问题 |
| 输入       | 还没定下来的设计，加上对照做法   | 计划或待办清单           | 代码变更差异           |
| 输出       | 典型场景、问题场景、供选择的方案 | 逐条核查结论             | 问题清单               |

## 场景库（挑 3 到 5 个用，不要每次都挑同一组）

### 一、时间与积累

- 第一天用和用了三年，行为有区别吗？
- 数据从 50 条长到 5 万条，哪一步会先撑不住？
- 有没有只在特定时间点才暴露的问题，比如跨月、跨年、月末最后一天写入。

例：用户连续记了两年日记，某天打开搜索，要等四十秒才出结果，因为每次启动都会全量重算一遍。

### 二、人与角色

- 第一次打开应用的新用户，看到的是空白、示例，还是一个需要先配置才能用的界面？
- 从旧版本升级上来的老用户，旧数据会被怎么处理？
- 同一个人在不同状态下的用法：赶时间随手记一句，和周末坐下来慢慢整理。

例：新用户还没配置嵌入模型就点了「开始整理」，得到一句提示，但提示里指的那个页面默认不在侧边栏上，他没法就地解决。

### 三、设备与并发

- 两台设备在同一时间段各写了一条，同步时是按行合并还是整份覆盖？
- 一台设备离线一周，另一台每天都在改，离线那台连上后先上传还是先下载？
- 换一台全新设备，只下载不上传，能不能完整恢复？

例：电脑上新增了一条记忆，手机上删掉了另一条，两边都改了同一个月份的文件，同步后两个动作都要保留。

### 四、中断与失败

- 断网、接口报错、进程被强制关闭、磁盘写满、权限被拒绝，分别停在哪一步？
- 停下来之后，本地留下的是完整状态还是半成品？
- 下次启动能不能自己发现没做完并接着做，还是要用户手动重来？

例：文件已经同步完了，但生成向量索引时断网，只写进去一半。下次打开要能看出缺了哪些并补齐，而不是当作已完成。

### 五、误操作与后悔

- 删错了能找回吗？找回的是原来那条还是一条新的？
- 同一个操作点两次会怎样？
- 用户以为自己在撤销，系统会不会理解成一次新的覆盖？

例：用户删掉一条记忆，几天后又记了一条内容很像的。旧的要保持删除状态，新的要能正常写进去，不能被判成重复而丢掉。

### 六、认知落差

这一类最容易变成用户投诉，但最常被漏掉。

- 用户以为系统做了什么？实际做了什么？
- 界面上显示的数字、状态、提示，和后台真实状态一致吗？
- 不一致的时候，用户会怎么解释他看到的现象？

例：界面显示「已同步」，用户以为换台设备就能搜到，实际上同步的只有原文，索引还要在新设备上重新生成，期间搜索是空的。

### 七、规模与等待

- 这个操作要等多久？有进度提示吗？
- 会不会卡住界面？
- 在后台跑的时候，用户正在写东西会被打断吗？

例：同步完成后自动开始批量生成索引，占满了请求配额，用户此时正在和伙伴对话，对话开始变慢。

### 八、外部干预

- 用户直接用编辑器改了这些文件会怎样？
- 用别的工具同步了同一个目录会怎样？
- 文件被挪走、改名、只剩一半，程序怎么反应？

例：用户手动编辑了某个月的记录文件，程序需要能发现内容变了并重新处理，而不是继续沿用旧的处理结果。

### 九、升级与回退

- 旧格式的数据怎么读？是就地迁移、并存，还是要求用户先导出？
- 新旧版本轮流打开同一份数据会怎样？
- 用户装回旧版本，新版本写的数据会不会被破坏？

### 十、平台差异

- 桌面端和移动端在权限、后台执行、存储位置上的差别，会不会导致行为不一致？
- 移动端被系统回收进程时，正在进行的操作停在哪里？

### 十一、空与极简

用来确认简单情况也成立，别为了照顾复杂场景把简单场景搞复杂。

- 完全没有数据时是什么样？
- 只有一条数据时是什么样？
- 从来不开同步的用户，这套机制对他有没有多余负担？

### 十二、可见性

- 哪些内容会离开这台设备？
- 用户看得到离开的是什么吗？
- 想撤回的时候能撤回吗？

## 写法：好例与坏例

**好的场景写法**

- 电脑上把李四的记录改了名字，手机上把张三的记录删了，两台都上传了八月份的文件，说明同步后两边各自看到什么。
- 手机一周没联网，电脑每天都在写，手机连上后第一个动作是上传旧文件，说明电脑上的新内容会不会被覆盖。
- 用户在配额用尽的情况下点了「全部重新生成」，说明跑到第几条会停、停下来界面显示什么、下次点进来从哪继续。

**不好的场景写法**

- 只说「并发时最后写入者优先更合理」，没有具体的人和动作。
- 只说「追加写入配合删除标记是有意义的」，机制成了主角，使用过程消失了。
- 场景里全是表名和函数名，读完不知道用户会看到什么。
- 五个场景全是多设备冲突，等于只推演了一个维度。

## 收束句式

> 现在要定的是：让 \_**\_ 这种用法更顺畅，代价是暂时不保证 \_\_** 这种用法。
> 选前者，实现可以简化成 \_**\_；选后者，就必须保留 \_\_**。

然后调用 `AskQuestion`，把上面两条变成可点选的选项，并把推荐的放在第一位。选项文字要写清「得到什么」和「放弃什么」，不要只写方案名。
