# 记忆管理 M1：落盘对齐与管理页

> 版本：v0.1（设计稿，未开工）
> 日期：2026-08-03
> 一句话：记忆管理页**已经存在**，但它的写路径全部绕过了新的 JSONL 落盘层——**删除会复活、编辑会回滚、手动添加不同步**。本方案先修数据一致性，再补管理能力。
> 前置：[记忆图谱与知识库设计方案.md](./记忆图谱与知识库设计方案.md) §2.1 写入铁律、附录 B.1

---

## 一、结论先行：这不是「做一个新页面」，是「修一个数据断裂」

调研后推翻了原本的判断。记忆管理页**两端都已经有了**，功能还相当完整：

| 端 | 入口 | 视图 |
| --- | --- | --- |
| 桌面 | 设置 →「RAG 记忆管理」（`agent.rag.title`） | `RagSettingsPane` → `packages/ui/src/desktop/RagMemoryView/` |
| 移动 | 设置 → RAG 记忆 | `RAGMemorySection` → `packages/ui/src/native/RagMemoryView/` |

已有能力：开关、统计 chips、检索参数、模型 mismatch 迁移、语义/文本搜索、分页列表、单条编辑、单条删除、手动添加、清空全部、批量嵌入未索引日记。

**问题在于这套 UI 是在「记忆只存 SQLite」的时代写的，而这轮开发把真相源换成了 JSONL，UI 却没跟着改。**

## 二、三条断裂的写路径

本轮 `d8d5161c` 之后，记忆的真相源是 `Memory/YYYY-MM.jsonl`，`memory_embeddings` 只是派生索引。写入铁律要求「白名单只经总/子 Manager」。但下面这些路径**直接改数据库**：

| 入口 | 实际行为 | 是否碰 JSONL |
| --- | --- | --- |
| `rag:delete-entry` | `DELETE FROM memory_embeddings WHERE embedding_id=?` | **否** |
| `rag:edit-entry` | `embeddingService.updateMemoryChunk` 重嵌同 id | **否** |
| `rag:add-manual-memory` | 仅 embed，`sourceType: 'manual'` | **否** |
| `memory_delete` 工具 | `deleteBySource(...)` | **否** |

对照正确范式——`memory_store` 工具是**先写 JSONL 再 embed**：

```133:159:packages/ai/src/tools/memory-store.tool.ts
      const written = await rawManager.writeRecord('memory', record)

      await embeddingService.embedText({
        text: contentToStore,
        sourceType: MEMORY_SOURCE_TYPE,
        sourceId: id,
        groupId: `memory:${context.vaultName}`
      })
```

而删除入口是这样的：

```176:179:apps/desktop/src/main/ipc/rag-query.ipc.ts
  ipcMain.handle('rag:delete-entry', async (_, embeddingId: string) => {
    const db = getAppDb()
    await db.delete(memoryEmbeddingsTable).where(eq(memoryEmbeddingsTable.embeddingId, embeddingId))
    return true
  })
```

### 2.1 后果一：删除会复活

用户在管理页删掉一条记忆，`memory_embeddings` 里没了，但 `Memory/2026-08.jsonl` 里那一行**仍是活行**（`deletedAt: null`）。

`MemorySyncService.syncPendingIndex()` 的逻辑是「读 pending 分片 → tombstone 行则删向量 → 活行则嵌入」。所以只要那个分片再次进入 pending 状态，这条记忆就会**被重新嵌入回来**。

触发时机：

- 换新设备，从 JSONL 灌库
- 该月分片被同步下载覆盖（另一台设备写了新记忆）
- 用户点「重建索引」
- 外部改写 JSONL 导致 pending 失效（提交 `36551716` 专门处理过这个）

**这是最糟糕的一类 bug：不是每次都复现，取决于分片何时变脏。** 用户会觉得「我明明删了，怎么又回来了」，而且没有稳定复现路径。

### 2.2 后果二：编辑会回滚

`rag:edit-entry` 只更新了向量表里的 `chunk_text`，JSONL 里还是旧内容。同样在上述任一时机，重新灌库会把旧内容盖回来，**用户的修改静默丢失**。

### 2.3 后果三：手动添加的记忆永不同步

`rag:add-manual-memory` 写的是 `sourceType: 'manual'`，既不在 JSONL 里，也不属于 `'memory'` 类型。

后果分两面：好的一面是 orphan sweep 只扫 `'memory'`，所以它不会被误删；坏的一面是它**永远只存在于本机**，换设备就没了，而用户完全不知道「手动加的记忆」和「伙伴记的记忆」待遇不同。

### 2.4 为什么现在才暴露

因为这些 UI 在 main 上是**正确的**——那时候 `memory_embeddings` 就是唯一真相，删了就是删了。是这轮把真相源换成 JSONL 之后，旧 UI 才变成了违规写入。

**这类问题在架构迁移中很典型：新写了一条正确的路径（`memory_store`），却忘了旧路径还在绕过它。**

## 三、核心决策

### M-D1：所有记忆写入必须经 `RawDataSourceManager`，无例外

把三条 IPC 和一个工具全部改成「先改 JSONL，再更新派生库」，与 `memory_store` 对齐。

| 操作 | 正确实现 |
| --- | --- |
| 删除 | `rawManager.tombstone('memory', id)` → `deleteEmbeddingsBySource('memory', id)` |
| 编辑 | 写一条同 `id`、新 `content`、新 `updatedAt` 的行（LWW 覆盖）→ 重新 embed |
| 手动添加 | 组装完整 `MemoryRawRecord` → `writeRecord` → embed，`sourceType` 统一为 `'memory'` |

编辑之所以是「追加同 id 新行」而不是「原地改」，是因为 JSONL 分片的合并语义就是按 `id` 取最大 `updatedAt`（`mergeJsonlRecordSides`），追加天然满足跨设备 LWW。

### M-D2：删除必须是 tombstone，不能是物理删行

`MemoryRawManager.tombstone` 已经实现了正确语义——追加一条 `deletedAt=now` 的同 id 行：

```24:28:packages/shared/src/raw-data/memory-raw.types.ts
  tombstone(
    kind: 'memory' | 'graph',
    id: string,
    opts?: { collection?: string; shardMonth?: string }
  ): Promise<void>
```

**必须用 tombstone 而不是从 JSONL 里抹掉那一行**：如果物理删除，另一台设备的分片里还有活行，合并时会把它当成「对方新增」而复活。tombstone 才能在 LWW 里赢过活行（测试已覆盖 `tombstone wins on equal updatedAt`）。

### M-D3：`sourceType: 'manual'` 就地废弃，统一为 `'memory'`

手动添加的记忆和伙伴记的记忆在数据模型上没有区别，区别应该体现在**记录的元数据**上，而不是向量表的 `sourceType`。

`MemoryRawRecord` 已经有 `sourceSessionId`——手动添加时置 `null`，天然可区分。UI 上标注「手动」即可。

**升级要处理存量**：`sourceType='manual'` 的旧数据要一次性补写进 JSONL（沿用 `MemoryJsonlBackfillService` 的思路，`legacySourceId` 保留原 id），然后把向量行的 `sourceType` 改成 `'memory'`。不重新嵌入。

### M-D4：管理页要能看见「记忆的来源」

现在列表只显示文本，用户无法判断一条记忆是哪来的。`MemoryRawRecord` 里的信息足够支撑：

| 展示 | 数据来源 |
| --- | --- |
| 来源会话 | `sourceSessionId`，可点击跳转对话 |
| 标签 | `tags` |
| 记录时间 | `createdAt` |
| 最后修改 | `updatedAt` |
| 手动/伙伴 | `sourceSessionId === null` |

这是管理页真正缺的东西——现有 UI 做了很多检索参数配置，却没告诉用户「这条记忆是伙伴在哪次对话里记下的」。

### M-D5：不做记忆的 Markdown 化

讨论过把记忆改成人可读的 Markdown，**否决**。Markdown 会丢掉已实现的行级 LWW 合并——两端各追加一段，整文件冲突只能选边，另一边的记忆直接丢失。要在 Markdown 上恢复这个能力，就得定义 id、`updatedAt`、删除标记的结构化格式再写一套解析合并，等于把 JSONL 重做一遍。

「可读可编辑」的诉求由**本管理页**满足，这才是它存在的意义。

## 四、数据一致性自检

修完之后，应该满足这条不变式：

> 任何时刻，`memory_embeddings` 中 `source_type='memory'` 的行集合，等于所有 `Memory/*.jsonl` 中 `deletedAt === null` 的行集合（按 id）。

建议在管理页加一个**一致性自检**入口（开发期常用，用户侧可放进「高级」）：

```
JSONL 活行 245 条 · 向量索引 245 条 · 一致 ✓
JSONL 活行 245 条 · 向量索引 243 条 · 缺 2 条 [重新索引]
JSONL 活行 245 条 · 向量索引 247 条 · 多 2 条孤儿 [清理]
```

这个检查复用现成能力即可：`listSourceIdsByType('memory')` 对比 `MemoryRawManager.listShards()` + `readShardRecords`，正是 `MemorySyncService` 的 orphan sweep 已经在做的事。

## 七、风险

**风险 1：`embedding_id` 与 `source_id` 的多对一关系被忽略。**
一条记忆可能切成多个 chunk，共享同一 `source_id`。删除若只按 `embedding_id` 删一行，会留下半条记忆在索引里。必须按 `source_id` 整条删。

**风险 2：tombstone 写进了错误的分片。**
`tombstone` 支持 `shardMonth` 提示；不传就要扫全部分片找 id。记忆量大时这是全表扫描。建议删除时把 `createdAt` 一并传下去推导分片月，避免线性扫描。

**风险 3：`'chat'` 类型记忆不在 JSONL 管辖内。**
`memory_delete` 按 `message_id` 删的是 `sourceType='chat'` 的向量，那是会话消息的嵌入，不是记忆记录，**不应该**去 tombstone JSONL。改造时要按 `sourceType` 分支，别一刀切。

**风险 4：迁移期新旧数据并存。**
M1.0 上线后，此前 UI 删除过的记忆仍在 JSONL 里当活行躺着，随时可能复活。**M1.0 应该附带一次性对账**：把「JSONL 有活行但向量表没有」的记录列出来，让用户选择「确认删除（补写 tombstone）」还是「恢复索引」。不做这一步的话，修完 bug 之后老用户仍会遇到一次复活。

**风险 5：清空全部记忆的代价。**
`rag:clear-all` 若要写 tombstone，意味着给每条记忆追加一行，分片体积翻倍。可以考虑对「清空」做特殊处理——直接把所有分片重写为纯 tombstone 集合，而不是追加。
