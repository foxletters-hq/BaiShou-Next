## 一、路线与优先级

图谱的能力已经建成得差不多了（见 §二）。剩下的工作分成两段，**两段都要做，只是先后不同**：

| 段 | 内容 | 优先级 | 用户视角 |
| --- | --- | --- | --- |
| **第一段** | 伙伴在聊天中主动调用图谱 | 近期 | 伙伴说得出「你上次提到杭州是和毕业旅行一起说的」 |
| **第二段** | 图谱展示、审核、手动编辑、路径推理 | 靠后 | 用户能看见并修正自己的关系网 |

先做第一段的理由是**投入产出比**：图谱的数据层、抽取、检索全都已经就绪，缺的只是「伙伴知道该用它」，改动量小但效果直接。而展示层是从零开始的 UI 工程，投入大得多。

**第二段不是可选项。** 没有展示，用户无法验证图谱抽得对不对，也无法修正错误关系；pending 记录也缺少最终的处理出口。只是它可以晚一步。

## 三、第一段：让伙伴主动调用

### 3.1 前提问题：图谱大概率是空的

日记变更时 shadow 钩子只 `markPendingReextract`，不触发 LLM。真正跑抽取的入口**只有图谱页的按钮**——一个用户很少主动打开的页面。

工具的失败文案也在往那儿指路：

```46:53:packages/ai/src/tools/recall-relations.tool.ts
      return '图谱读取器未就绪。请先在图管理页抽取日记，或检查 Vault / 索引是否已灌入。'
      ...
        return `未找到与「${entity}」相关的图谱实体。可先在图管理页梳理待重抽日记。`
```

**没有数据，主动调用毫无意义。** 这是第一优先级。

### 3.2 模型不知道什么时候该调

工具描述写的是能力，不是时机：

```22:25:packages/ai/src/tools/recall-relations.tool.ts
  readonly description =
    'Recall people/places/events and their relations from the user memory graph. ' +
    'Use for explaining connections or timelines grounded in diary sourceRef excerpts. ' +
    'Read-only; does not modify the graph.'
```

「Use for explaining connections」太抽象，模型不会知道「用户说『上次和小明去的那家店』时应该查图谱」。

### 3.3 Gate 问过了，却还要再审核一次

`graph_upsert` 写入时**恒为 `pending`**，而 `GraphRagService` 强制 `approvedOnly: true`：

```
伙伴想写关系 → Gate 弹窗问用户 → 用户点「允许」→ 写入 pending
                                                    ↓
                                        伙伴自己查不到（approvedOnly）
                                                    ↓
                                      用户还得去图谱页再批准一次
```

用户在 Gate 弹窗里已经看到 summary、entities、edges 并点了允许——**那就是审核**。让他去另一个页面批准第二次既冗余又反直觉。

而且第二道审核的 UI 属于第二段，优先级靠后。**在它做好之前，`graph_upsert` 写进去的东西全部不生效。**

## 四、第一段的核心决策

### G-D1：抽取入口迁移到日记侧

图谱页仍然保留抽取入口，但不再是唯一入口。新增两个更自然的位置：

**位置一：日记保存后的轻提示。**

```
已保存 · [让伙伴记住这篇里的人和事]
```

点了就抽这一篇，即时、可见、成本明确。不点就算了。**只在该篇未整理过时显示**，且是一行低调提示而非弹窗。

**位置二：日记列表的批量入口。** 显示「有 N 篇日记还没整理」，点击后批量抽取并显示进度。

两个位置的共同点是：**用户正在想日记的时候，才提图谱的事**。只在图谱页提是本末倒置——用户会去图谱页，本来就是因为他已经知道有图谱。

### G-D2：先做手动触发，自动抽取留到第二段

不做空闲自动抽取。LLM 抽取要花钱，自动化涉及空闲检测、电量、网络条件、并发控制、失败退避，复杂度高，而**手动入口放对位置就已经能解决大部分问题**。

先观察 G-D1 两个入口的使用情况，再决定自动化的形态。

### G-D3：经 Gate 明确允许的写入直接 `approved`

**第一段最关键的一条。**

`graph_upsert` 通过 Gate 询问后，应写 `reviewStatus: 'approved'` 而非 `pending`。理由是 Gate 弹窗展示了完整内容，用户点「允许」即知情同意——这与用户手动通过 `graph:upsert-edge` IPC 写入的语义完全相同，**而后者写的正是 `approved`**。同一件事不该有两个标准。

`pending` 保留，但只用于**没有经过人确认的路径**：

| 写入路径 | reviewStatus | 理由 |
| --- | --- | --- |
| `graph_upsert` 经 Gate 允许 | **`approved`**（改） | 用户在弹窗里确认过 |
| `graph_upsert` 在 Allow 规则下自动放行 | **`approved`**（改） | 用户设 Allow 就是预先授权 |
| 日记抽取 confidence ≥ 70 | `approved`（不变） | 已有策略 |
| 日记抽取 confidence < 70 | `pending`（不变） | 模型自己也不确定 |
| 用户手动 IPC 写入 | `approved`（不变） | 用户直接操作 |

**凡是过了 Gate 的 `graph_upsert` 一律写 `approved`**，不区分是当场允许还是规则放行。用户把 `graph_upsert` 设成 Allow，本身就是「我信任伙伴记录关系」的表态，没有理由再把结果扣在 pending 里——那等于把一个用户主动放宽的设置变成了「写入静默失效」。

因此**第一段不需要改动 Gate 链路**：工具不必知道自己是被明确允许还是被规则放行，直接写 `approved` 即可。

`pending` 因此收窄为只有一个来源：**日记抽取里 confidence < 70 的低置信关系**。这也让 pending 的语义变干净了——它表示「模型自己不确定」，而不是「流程还没走完」。

### G-D4：只读检索自动放行，不进 Ask

`recall_relations` 目前没有 Gate metadata，走默认。**应保持自动放行。**

如果每次伙伴想查图谱都弹窗问用户，对话体验会彻底崩溃——用户要的是「伙伴自然地记得」，不是「伙伴每次回忆前先申请许可」。只读、不出网、不改数据，风险为零。

需要询问的是**写入**，读取不在此列。

### G-D5：调用时机写进工具描述，而非系统提示词

系统提示词是每轮对话的固定成本；工具描述只在工具启用时进上下文，且与工具内聚，不会随伙伴人设改动而丢失。

描述要写**什么时候用**：

```
Recall how people, places, and events in the user's life connect to each other.

Call this when:
- the user refers to a past event, person, or place assuming you already know it
  ("那家店", "上次和他一起", "毕业旅行的时候")
- you want to mention a connection between two things the user has told you about
- the user asks why/how two things are related

Returns relation paths with excerpts from the original diary entries, so you can
say where you know it from. Read-only.
```

**关键是给出触发线索的例子。** 指代性表达是最强的信号——用户在假设伙伴知道，而伙伴恰好可以去查。

### G-D6：空图谱要让模型放弃，而不是反复尝试

当前空图谱文案指向图管理页，措辞像是「你可以去修好它」，模型可能反复尝试或转述给用户。改成对模型明确的终止信号：

```
The memory graph has no data yet. Do not call this tool again in this conversation.
```

同时**不要让用户看到内部错误**。伙伴应自然绕过，而不是说「图谱读取器未就绪」。

## 五、第二段：图谱展示与管理

优先级靠后，但下列设计已经想清楚，做的时候直接用。

### G-D7：管理页与 Agent 必须看同一个图

`getGlobalGraph` 不过滤 `reviewStatus`，而 `GraphRagService` 强制 `approvedOnly: true`。结果是用户在图谱页看到一条边，问伙伴却说不知道——**这会严重损伤信任**。

修法不是给管理页也加过滤（那样用户就看不到待审的东西），而是**视觉区分**：

| 状态 | 画法 |
| --- | --- |
| approved | 实线，正常颜色 |
| pending | 虚线，降低不透明度，点击可直接审核 |
| rejected | 不画 |

图例说明「虚线的关系伙伴还看不到，需要你确认」。用户既能看到全貌，又清楚哪些是生效的。配一个「只看已确认」的开关，默认关闭但容易找到。

### G-D8：节点审核补齐，与边同构

`graph_nodes.reviewStatus` 字段存在但**没有任何流转路径**——无 IPC 无 UI，这是个半成品。补 `graph:set-node-review`，与 `graph:set-edge-review` 同构（`rejected` → `deletedAt = now`）。「待确认」Tab 要同时列出待审节点和边，当前只列边。

**顺序约束**：一条边的端点若是 pending 节点，批准边时应连带批准节点，否则会出现「边生效了但端点在 Agent 侧不可见」的悬空状态。

### G-D9：手动编辑 UI 接已有 IPC

`graph:upsert-node` / `graph:upsert-edge` / `graph:soft-delete` **都已实现**，写入 `origin: 'user'` + `reviewStatus: 'approved'`，preload 也暴露了，**只差 UI**：

- 节点详情面板改名 / 改摘要 / 加别名
- 从节点详情发起「添加关系」，选目标节点 + 关系类型（`GRAPH_EDGE_TYPES` 枚举）
- 删除边、软删节点

`origin: 'user'` 的记录在重抽时不会被 supersede（`supersedeAiEdgesBySourceRef` 只处理 `origin='ai'`），**用户的手工修正是安全的**——这个保护已经实现了，UI 上要让用户知道。

**任何用户编辑都应把 `origin` 置为 `user`**，这样自动获得重抽保护，否则改完会被 AI 覆盖。

### G-D10：首次引导要给出成本预估

用户第一次打开图谱页时若有待抽日记，不要显示空白画布：

```
┌─────────────────────────────────────────────┐
│  还没有开始整理你的关系图谱                   │
│                                             │
│  发现 128 篇日记可以分析，预计消耗            │
│  约 6.4 万 tokens（按当前模型约 ¥0.3）        │
│  用时约 4 分钟                               │
│                                             │
│  [开始整理]   [以后再说]                     │
└─────────────────────────────────────────────┘
```

**必须给预估成本和时间**，这是用户做决定所需的全部信息，而这些数字都算得出来。文案用「约」并给区间，**宁可高估**——实际更便宜是惊喜，反过来是事故。

### G-D11：推理返回路径，而非边集

现在 `network` 模式返回 2 跳邻域的边列表，模型拿到一堆散边要自己拼关系链。改为返回**路径**：

```
问：小明和杭州有什么关系？
现在：返回小明的所有边 + 杭州的所有边，模型自己找交集
改进：返回 [小明 --参与--> 毕业旅行 --发生于--> 杭州]，附每条边的原文摘录
```

实现是把 BFS 换成两端点间的最短路径搜索。`sourceExcerpt` 已经存了原文摘录，正好支撑「为什么这么说」。

**深度不要放开**，限 2–3 跳。个人日记规模下，3 跳以上的路径几乎都是噪音（任何两个实体都能通过「我」连起来），还会撑爆上下文。

### G-D12：i18n 词条化

图谱页全部是 `t('graph.xxx', '中文 fallback')`，**没有词条文件**，切到英文/日文界面仍是中文。要把 `graph.*` 补进四个语言文件（桌面 ~24 个 key + 移动端额外 ~9 个）。

纯体力活但发版前必做——这是少数几个完全没有国际化的界面。

### G-D13：桌宠单独立项

桌宠可以成为图谱的一个表现层，但它本身是独立产品形态（常驻窗口、交互模型、资源占用），不该混进图谱方案。等图谱与知识库稳定后再说。

## 八、风险

**风险 1：抽取入口挪到日记侧后打扰用户。**
日记保存是高频动作，每次提示会烦。缓解：只在该篇未整理过时显示，低调一行而非弹窗，用户忽略几次后不再对这篇提示。

**风险 2：Allow 规则下的自动写入仍是 pending 黑洞。**
若用户把 `graph_upsert` 设成 Allow（不再询问），所有写入都是 pending，而审核 UI 在第二段——期间完全没有出口。**倾向于 Allow 规则下也写 `approved`**（用户选了 Allow 就是接受了），但需在 G1.1 明确决定，不要悬着。

**风险 3：模型调用过于频繁。**
每句话都查图谱会拖慢响应、烧 token。缓解：描述强调「指代性表达」而非「任何提到人名时」。上线后观察实际调用频率。

**风险 4：空图谱时模型反复尝试。**
G-D6 的终止信号要对模型明确。若仍重试，考虑在会话级缓存「本会话图谱为空」直接短路。

**风险 5：第一段期间无从排查抽取质量。**
现有 `GraphPage` 保留为调试窗口，**不要删**——抽取质量、pending 堆积、边类型分布只有看到图才能判断。第一段不投入新功能，但要保证能打开。

**风险 6：自动抽取烧掉用户额度（第二段）。**
最严重的风险。必须先经用户明确同意、给出预估、随时可停、失败退避、进度可见。**任何情况下都不能在用户没点过头时跑 LLM。**

**风险 7：路径搜索在稠密图上退化（第二段）。**
个人图谱里「我」会连接几乎所有东西，双向 BFS 经过它会爆炸。**需对超高度数节点特殊处理**——排除，或在路径里标注「通过你」这种弱连接。这是路径推理能否有用的关键，不解决则返回的路径全是噪音。
