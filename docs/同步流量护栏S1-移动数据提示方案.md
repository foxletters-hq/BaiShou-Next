# 同步流量护栏 S1：移动数据下的流量提示

> 版本：v0.2
> 日期：2026-08-04
> 一句话：同步计划里补上**字节统计**，在移动数据下超过阈值时把流量摆给用户看，Wi-Fi 永不打扰。
> 关联：从 [知识库K1-向量笔记本方案.md](./知识库K1-向量笔记本方案.md) D11 拆出——这是**通用能力**，日记附件与聊天附件同样受益，不该挂在知识库下面。
> **实现进度：S1.0–S1.3 已落地**（计划层汇总字节 + 确认弹窗展示上下行流量；网络类型感知；移动数据超阈值警告与「等 Wi-Fi」；Wi-Fi 回连轻提示；双端 OfflineBanner 挂载）
> **定位：S1 是 UI 护栏**（确认弹窗），不是传输硬拦截；用户仍可选择继续。

---

## 一、为什么单独立项

原本这条护栏写在知识库方案里，因为讨论是从「知识库要不要同步 PDF 原文」引出的。但它其实和知识库没有必然关系：

| 已经存在的大流量来源 | 量级 |
| --- | --- |
| 日记附件（图片、视频） | 按每篇配一张图算，5 年接近 1 GB |
| 聊天附件与背景图 | 单张可达数 MB |
| 全量归档恢复 | 一次性拉取整个 vault |
| 知识库 PDF 原文（未来） | 文本型约 2 MB/份，扫描型约 20 MB/份 |

**先撞墙的多半不是知识库，而是日记附件**——这个约束今天就存在。所以护栏应该现在做，且不依赖知识库落地。

另一个理由是排期解耦：知识库 K1 是一个跨越多期的大工程，护栏挂在它下面会被一起延后。

## 二、现状：数据都在，只是没被统计

### 2.1 字节数在合并层是齐全的

`MergeDecision.size` 是必填字段，来自 `ManifestEntry.size`（字节）：

```13:24:packages/shared/src/sync/three-way-merge.ts
export interface MergeDecision {
  filePath: string
  type: 'upload' | 'download' | 'delete-local' | 'delete-remote' | 'skip' | 'conflict-resolved'
  /** 冲突时的数据流向 */
  direction?: 'upload' | 'download'
  hash: string
  size: number
  ...
}
```

### 2.2 但计划层把它丢掉了

`toPlanItem` 只保留路径、动作、vault 归属：

```123:132:packages/shared/src/sync/incremental-sync-plan.util.ts
function toPlanItem(decision: MergeDecision): IncrementalSyncPlanItem | null {
  if (decision.type === 'skip') return null
  const action =
    decision.type === 'conflict-resolved' ? ('conflict-resolved' as const) : decision.type
  return {
    filePath: decision.filePath,
    action,
    vaultScope: resolveIncrementalSyncVaultScope(decision.filePath)
  }
}
```

`IncrementalSyncVaultSummary` 同理，只有 `upload` / `download` / `deleteLocal` / `deleteRemote` / `conflict` 五个**计数**，没有字节。

所以用户在确认弹窗里看到的是「本次将变更 128 个文件」——**128 个文件可能是 2 MB，也可能是 2 GB，界面上完全看不出区别**。

### 2.3 网络类型没有被读取

移动端有 NetInfo，但只取了两个字段：

```32:36:apps/mobile/src/providers/NetworkProvider.tsx
function resolveNetworkStatus(state: NetInfoState | null): NetworkStatus {
  const isConnected = state?.isConnected ?? true
  const isInternetReachable = state?.isInternetReachable ?? null
  const isOnline = isConnected && (isInternetReachable === null || isInternetReachable === true)
  return { isConnected, isInternetReachable, isOnline }
}
```

`state.type`（`'wifi'` / `'cellular'` / …）**全仓库未使用**。桌面端的 `NetworkProvider` 用的是 `navigator.onLine`，只有在线/离线，没有连接类型——这是合理的，桌面本来也不该管这件事。

### 2.4 「先提示再执行」的范式已经有了两套

不需要发明新机制，照抄即可：

| 已有范式 | 实现 |
| --- | --- |
| 高分歧确认 | `requiresHighDivergenceConfirm` + `divergencePercent` 进 preview → 弹窗展示 `plan_warning_high_divergence` → 确认时带 `highDivergenceConfirmed: true` |
| 删除传播选择 | `requiresDeletePropagationChoice` + `blockedDeleteCount` → 弹窗给三选一按钮 |

两者都是「计划阶段标记 → 确认弹窗展示 → 用户选择 → 执行时带上决定」。流量护栏是同一个形状。

## 三、核心决策

### S-D1：字节统计进计划层，upload 与 download 分开算

`IncrementalSyncPlanItem` 加 `sizeBytes`，`IncrementalSyncVaultSummary` 加 `uploadBytes` / `downloadBytes`，preview 顶层加合计。

**上下行必须分开**，因为它们对用户的意义不同：下行吃流量套餐，上行在很多网络下更慢。界面上「下载 340 MB / 上传 12 MB」比「共 352 MB」有用得多。

归类规则跟着 `type` 走，冲突项按 `direction` 归：

| decision.type | 归入 |
| --- | --- |
| `upload` | uploadBytes |
| `download` | downloadBytes |
| `conflict-resolved` | 按 `direction` 归入对应方向 |
| `delete-local` / `delete-remote` | **不计入**，删除不产生传输 |

删除不计流量这点要写清楚，否则「删 500 个文件」会被算成巨大流量，把用户吓住。

### S-D2：判定只在移动数据下生效，Wi-Fi 永不提示

```
if (networkType === 'cellular' && totalBytes > threshold) → 提示
else → 静默同步
```

**Wi-Fi 下不做任何提示**，包括不显示"本次将传输 2 GB"这种信息——那只会制造焦虑而没有可操作性。用户在 Wi-Fi 下本来就不该关心流量。

网络类型未知时（`type === 'unknown'` 或 NetInfo 未就绪）**按 Wi-Fi 处理**，即不提示。理由是宁可漏提示也不要误报：在 Wi-Fi 下被反复询问流量，用户会直接关掉这个功能，护栏就永久失效了。

### S-D3：复用现有确认弹窗，不新建

`IncrementalSyncConfirmDialog`（双端已有）本来就是「计划确认」的载体，且已经承载了高分歧警告和删除传播选择。流量信息应该长在它上面。

**始终显示流量摘要**（一行，中性语气），只有触发条件成立时才升级为**警告样式 + 追加操作选项**：

```
┌─ 确认同步 ─────────────────────────────────┐
│ 当前工作区：Personal                        │
│ 本次将变更 128 个文件                        │
│ 下载 340 MB · 上传 12 MB          ← 始终显示 │
│                                             │
│ ⚠ 正在使用移动数据，本次约需 352 MB          │
│                                   ← 仅触发时 │
│                                             │
│      [取消]  [等 Wi-Fi 再同步]  [继续同步]   │
└─────────────────────────────────────────────┘
```

「等 Wi-Fi 再同步」是取消同步 + 记一个标记，等检测到 Wi-Fi 时提醒用户（或自动执行，见 S-D5）。

**沿用现有的 3 秒倒计时**（`SYNC_CONFIRM_DELAY_MS`），避免用户下意识连点确认。

### S-D4：阈值配置存本地设备，不进同步配置

增量同步的配置在存储根的 `.baishou-s3.json`（`S3SyncConfig`）。**流量护栏的配置不能放这里**，因为它是**设备相关**的：手机有蜂窝网络，桌面没有；用户的手机套餐和平板套餐可能也不同。

配置项：

| 项 | 默认值 | 说明 |
| --- | --- | --- |
| 启用流量提示 | 开 | 关掉后永不提示 |
| 提示阈值 | 50 MB | 移动数据下超过此值才提示 |

放在移动端本地设置里，与增量同步配置分开。桌面端**不提供**这两项——桌面没有连接类型感知，做了也是摆设。

### S-D5：「等 Wi-Fi」要真的有后续，否则就是「取消」的别名

如果点了「等 Wi-Fi 再同步」之后什么都不发生，这个按钮就是骗人的。两种做法：

**方案 A（推荐，K1 范围）**：记一个 pending 标记，`NetworkProvider` 检测到从 cellular 切到 wifi 时，弹一个轻提示「已连上 Wi-Fi，现在同步？」。实现简单，用户始终掌握控制权。

**方案 B（后续可选）**：Wi-Fi 下自动执行。体验更好但要处理后台执行、失败重试、用户不在场时的冲突确认，复杂度高得多。

先做 A。`useNetworkStatus` 已经是个 hook，加 `type` 之后监听切换是顺手的事。

### S-D6：顺带把离线横幅挂上

调研发现 `NetworkOfflineBanner` 在**双端都已实现但从未挂载**——桌面 `App.tsx` 和移动 `_layout.tsx` 都只包了 `NetworkProvider`，没渲染横幅。

这属于「代码写了但没接线」，顺手接上即可，与本方案同属网络感知范畴。

## 六、风险

**风险 1：`ManifestEntry.size` 可能不准。**
字节数来自 manifest，若 manifest 与磁盘实际不一致（外部改写、同步中断），显示的流量会有偏差。这是**提示性信息**，允许偏差，但不要拿它做硬阻断。

**风险 2：在 Wi-Fi 下误报会让用户直接关掉护栏。**
所以 S-D2 明确规定网络类型未知时按 Wi-Fi 处理。宁可漏提示也不要打扰——一个被关掉的护栏等于没有。

**风险 3：删除被算进流量。**
`delete-local` / `delete-remote` 的 `size` 字段是有值的（来自被删文件的 entry），但删除不产生传输。聚合时必须排除，否则「清理 500 个旧文件」会显示成巨大流量。这是最容易写错的一处，单测要覆盖。

**风险 4：「等 Wi-Fi」变成假按钮。**
见 S-D5。如果 S1.3 不做，这个按钮就应该改叫「取消」，不要给用户虚假承诺。

**风险 5：首次同步的流量窗口无法避免。**
新设备接入时必然要拉全量，护栏能做的只是**告知**，不能减少。真正的缓解是让用户知道「这是一次性的」——警告文案里要说明这点，否则用户会以为每次同步都这么大。
