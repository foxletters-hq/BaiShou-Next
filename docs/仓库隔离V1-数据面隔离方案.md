# 仓库隔离 V1：数据面隔离

> 版本：v0.1（设计稿，未开工）
> 日期：2026-08-04
> 一句话：工作空间（Vault）在**磁盘层**是隔离的，在**派生索引层**基本没隔离——会话列表、向量检索都不按仓库过滤，删除仓库也不清库。本方案把数据面一次性做透。

> **实现进度：V1.0–V1.4 已落地**（`vault_id` 列 + 回填、检索 SQL 层过滤、会话列表过滤、删除仓库清库、总结/助手按 vault_id 共存），未发布；V1.5–V1.7 未开工

## 一、结论先行：隔离只做了磁盘那一半

工作空间的**文件布局**是完整的：目录按 `<VaultName>/Journals|Archives|Sessions|Memory|Graph|Assistants` 分开，注册表 `vault_registry.json` 管理列表，增量同步按路径第一段分 scope。这一层没问题。

问题全部出在**派生索引层**。所有工作空间共用一个 `baishou_agent.db`，切换仓库不换库：

```9:14:apps/desktop/src/main/db.ts

  if (workspaceRoot && workspaceRoot.trim() !== '') {
    return resolveSharedAgentDbPath(workspaceRoot)
  }
  return join(app.getPath('userData'), 'baishou_agent.db')

```

同库多仓库本身没错，错在**大量查询根本不按仓库过滤**，以及三张关键表干脆没有仓库维度。

## 四、根因分析

### 4.1 `group_id` 是杂物列，装不下仓库维度

`memory_embeddings` 没有仓库字段：

```15:29:packages/database/src/schema/vectors.ts
export const memoryEmbeddingsTable = sqliteTable('memory_embeddings', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  embeddingId: text('embedding_id').notNull().unique(),
  sourceType: text('source_type').notNull(),
  sourceId: text('source_id').notNull(),
  groupId: text('group_id').notNull(),
```

`group_id` 被当成万能分组用，同一列里混着性质完全不同的值：

| 写入方 | `group_id` 取值 | 含仓库？ |
| --- | --- | --- |
| 记忆 | `memory:Personal` | 是 |
| 日记（新） | `diary:Personal` | 是 |
| 日记（旧批次） | `diary_batch` / `diary_auto` / `diary_post_sync` | 否 |
| 聊天 | 会话 ID | 否 |
| 手动记忆（遗留） | `manual` / `manual_memory` | 否 |

**所以「加个 where 条件」这条路走不通**，必须引入真正的仓库列。

### 4.2 检索是后置过滤，且只挡日记

现有隔离靠一个 JS 侧的结果过滤函数，注释直白地写着其它类型放行：

这是当年有意为之的半措施。管理页列表那边是同一套逻辑的另一份实现：


意思是「只要不是日记，一律放行」。

**这段历史值得记一笔**，因为它解释了当前状态的成因：手动记忆功能 2026-04-07 上线（`1c54caa2`），`group_id` 直接写死 `'manual'`——在那个时间点是自洽的，因为读取侧本来就不看仓库。直到 2026-06-27 日记 RAG 撞上跨仓库问题，才有了 `93756b33` 与 `e9745685` 两个提交补隔离，上面这两处过滤都是那次加的。修法是「哪疼治哪」，只覆盖日记，没有延伸到记忆与聊天。

所以本期不是「新加一个能力」，而是**把当年那次只做了三分之一的隔离补完**。在新定位下，现有实现有三个问题：

1. **只挡日记**，记忆、聊天完全放行
2. **后置过滤伤召回**：SQL 层取回 top-K 之后才筛，如果前 30 条里有 20 条属于别的仓库，筛完只剩 10 条
3. **桌面端是另写一份内联过滤**（`rag-query.ipc.ts` 里手写 `r.sourceType !== 'diary' || r.sessionId === vaultDiaryGroupId`），两端各一套，容易漂移

而 SQL 层的过滤条件里根本没有仓库：

```39:42:packages/database/src/repositories/hybrid-search.repository.vector-search.ts

      conditions.push(`${columnPrefix}source_type = ?`)
      args.push(filter.sourceType)
    }
```

`agent_sessions` 表**有** `vault_name` 列，但列表查询的条件里只有助手 ID 和搜索词：

伙伴那边更激进——`fullResyncFromDisks` 会**删掉当前仓库磁盘上没有的助手行**（`assistant-manager.test.ts` 里有专门用例断言这个行为）。等于每次切换都做一次「清空 + 重灌」。

这套做法的代价：切换期间存在不一致窗口；重建失败就残留 ghost；助手数据实际经历了删除再插入，任何依赖行 id 的东西都会断。

### 4.5 设置的方向反了

应用设置按契约应该是**全局**的，但它写在活跃仓库内部：


**注意这一条的修复方向与前面相反**：不是给设置加仓库维度，而是把它从仓库里搬出去。

## 五、核心决策

### V-D1：给 `memory_embeddings` 加 `vault_name` 列，不再靠 `group_id` 推断

新增列 + 索引，写入时必填，检索时在 SQL 层过滤。`group_id` 保留原语义（批次 / 会话分组），不再承担仓库职责。

理由：`group_id` 已被四种写入方以不同约定占用，任何基于字符串前缀的推断都是脆的；而列是显式的、可加索引的、迁移一次就永久干净。

### V-D2：检索一律 SQL 层过滤，删除所有后置过滤

`QueryFilter` 增加 `vaultName`，`buildWhereClause` 落到 SQL。随后删除 `filterDiaryScopedSearchResults` 及桌面端那份内联过滤——它们在 SQL 过滤生效后不仅冗余，还会继续吃掉召回配额。

**这一步顺带修好了召回质量问题**：top-K 从一开始就只在本仓库里取。

### V-D3：会话列表按活跃仓库过滤

`findAllSessions` 补 `vault_name` 条件。同时检查其余会话查询入口（搜索、统计、导出）是否有同样遗漏。

### V-D4：`summaries` / `agent_assistants` 加仓库列，废除「切换时重建」

两张表各加 `vault_name`，查询按活跃仓库过滤。之后：

- `rebindSummaryCacheForActiveVault` 的 ghost 清理不再需要
- `fullResyncFromDisks` 不得再删「当前仓库磁盘上没有」的行——它只能管自己仓库那一份

这会让切换变快（不用清空重灌），也消除切换期的不一致窗口。

### V-D5：设置搬出仓库，放到存储根

设置目录从 `<Vault>/.baishou/settings/` 改为存储根下的 `.baishou/settings/`，使其真正全局。

**同步影响**：增量同步现在按路径第一段判定 scope，根级文件不在任何仓库 scope 内。需要给同步引入一个 `global` scope 覆盖根级 `.baishou/settings/`。这是 V1 里唯一需要动同步引擎的地方，风险最高，**建议单独一个提交并配套迁移测试**。

存量迁移：首次启动时，若根级设置不存在而活跃仓库内存在，则搬过去；其余仓库内的旧设置文件重命名为 `.migrated` 保留一个版本，不直接删。

### V-D6：删除仓库时清干净派生数据

`deleteVault` 之后补一步 `purgeVaultDerivedData(vaultName)`，覆盖 `agent_sessions`（级联消息 / parts）、`memory_embeddings`、`graph_nodes` / `graph_edges`、`diary_embed_jobs`、`summaries`、`agent_assistants`。

**必须在删目录之前先删库**，否则删库中途失败会留下「目录没了、索引还在」的幽灵态；反过来则只是多占点空间，下次还能重删。

### V-D7：遗留手动记忆复制到每个仓库，原件不动

`manual` / `manual_memory` 分组的旧记忆行里**没有任何仓库线索**（`source_id` 是 `manual_${timestamp}`）。它们在旧实现下是**全局可见**的——因为读取端根本不过滤仓库。所以「隔离之后只在一个仓库里能看到」对用户是可感知的退化。

M1.1 已经把这批记忆补写进了 JSONL，归到当时的活跃仓库（记为 X），并留下 `legacySourceId` 标记。据此：

| 动作 | 说明 |
| --- | --- |
| 原件 | 留在 X 不动，正常参与 X 的召回 |
| 副本 | 给**除 X 外**每个仓库各写一条新记忆：新 id、内容相同、`derivedFromLegacyId` 指回原件 |
| 幂等 | 重跑前先查目标仓库是否已有 `derivedFromLegacyId = 原id` 的行 |
| 新建仓库 | **不补副本**。这是一次性升级兼容，不是长期机制 |

**不要用「全局记忆」（`vault_name = '*'`）实现。** 看起来更省事，实则要付出两笔长期成本：记忆的孤儿清扫按仓库读 JSONL 活行集合，`'*'` 不属于任何仓库的集合会被当孤儿删掉，得专门开豁免；而 JSONL 文件只能待在一个仓库目录下，「全局」在向量层成立、在文件层是假的，同步时仍只跟着那一个仓库走。复制方案让每条记忆都实实在在属于某个仓库，落盘位置明确，同步语义不变。

副本之间各自独立，在 A 中编辑不影响 B——这符合完全隔离的定位，不是缺陷。

单仓库用户（多数）在这一步什么都不会发生。

## 六、存量回填：只有一类需要问用户

新增 `vault_name` 列后，存量行按下表回填：

| 类型 | 回填依据 | 可自动？ |
| --- | --- | --- |
| 记忆 | `group_id` 形如 `memory:X` → 取 `X` | 是 |
| 日记（新） | `group_id` 形如 `diary:X` → 取 `X` | 是 |
| 日记（旧批次） | `source_id` 形如 `X#42` → 取 `X` | 是 |
| 聊天 | `group_id` 是会话 ID → **join `agent_sessions.vault_name`** | 是 |
| 遗留手动记忆 | M1.1 已归到当时活跃仓库，JSONL 留有 `legacySourceId` | 是（原件），副本另见 V-D7 |

聊天这条是关键发现：会话表本来就有仓库列，join 一下就能把聊天向量的归属补齐，不用问用户。

**日记侧不存在长期无归属数据**：2026-06-27 那次改造对旧格式日记向量的处理是**删掉重嵌**而非保留（`purgeAllLegacyDiaryEmbeddings` 清掉 `source_id` 不含 `#` 或挂旧批次分组的行）。它挂在批量嵌入入口而非冷启动，所以升级后未跑过批量嵌入的用户仍可能有残留——回填时按空值处理即可，下次批量嵌入会自动清掉并重嵌成带仓库的格式。

`summaries` / `agent_assistants` 的回填更简单——它们本来就是「按活跃仓库磁盘重建」的产物，直接扫各仓库 `Archives/` 与 `Assistants/` 目录重建一次即可，这个能力现成。

## 九、验收：必须新增的多仓库测试

现有测试基本都在单仓库（`Personal` / `default`）下跑，切换与删除后的串数据完全没有守护。本期必须补上：

1. 建 A / B 两个仓库，各写日记 / 记忆 / 会话，在 A 中检索 → 不得出现任何 B 的行
2. 在 A 中让伙伴调用 `vector_search` → 结果全部属于 A
3. 切到 B → 会话列表不含 A 的会话；助手列表不含 A 的助手且 A 的助手行**仍在库里**
4. 删除 B → 全表按 `vault_name = 'B'` 扫不到任何行；A 的数据完好
5. 切换往返 A → B → A，主题 / 语言 / AI 配置不变
6. 回填迁移的幂等性：连跑两次结果一致

## 十、风险

**风险 1：`embedText` 加必填参数会波及大量调用点。**
分散在两端七八个文件里。建议**一次性改成必填**并靠类型错误找齐，不要用可选参数过渡——可选参数意味着漏掉的调用点会静默写入空值，而空值行在检索时要么被全过滤掉（记忆凭空消失）要么被全放行（隔离失效），两种都比编译失败难查。

**风险 2：回填期间的空值行怎么处理。**
迁移中途中断会留下部分空值。检索侧应显式定义空值语义：**建议按「不属于任何仓库」处理，即一律不返回**，并在一致性自检里暴露数量。绝不能默认放行，否则迁移失败会静默退化成现在的无隔离状态。

**风险 3：`summaries` 的唯一约束。**
现有约束建在「类型 + 起止日期」上：

```18:20:packages/database/src/schema/summaries.ts
  (t) => ({
    unq: unique().on(t.type, t.startDate, t.endDate)
  })
```

今天不冲突，是因为这张表同一时刻只装活跃仓库那一份。一旦按 V-D4 改成全仓库共存，约束必须一并改成「仓库 + 类型 + 起止日期」，否则两个仓库的同月总结会互相顶掉。这是本期唯一一处**改错了会丢用户数据**的地方。

**风险 4：设置搬家与同步的相互作用。**
根级 `.baishou/settings/` 若没被纳入同步 scope，表现是「设置从此不再跨设备同步」——用户不会立刻发现，等发现时已经分叉。V1.5 的测试必须覆盖两端同步，不能只测本地切换。

**风险 5：移动端迁移脚本同步。**
`embedded-agent-migrations.ts` 是脚本从桌面 drizzle 目录生成的。加列后若忘了跑同步脚本，移动端会在缺列的库上执行带 `vault_name` 的查询而直接报错。改 schema 的提交必须包含重新生成的产物。

**风险 6：删除仓库的顺序。**
先删库再删目录。反过来一旦中途失败，用户看到的是「仓库已消失但检索还能搜到它的内容」，且没有任何入口能再触发清理。
