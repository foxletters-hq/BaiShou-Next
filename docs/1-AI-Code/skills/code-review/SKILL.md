# 代码审查清单

审查对象是本次改动（diff、提交或用户指定的文件）。先确认范围，再逐项检查。不适用的条目直接跳过，不要为了填满清单而硬找问题。

## 1. 正确性与根因

- 改动真的解决了原始问题吗？能不能沿着代码推演出「问题不再发生」？
- 修的是根本原因，还是让症状不再出现？下面这些信号说明可能只是在掩盖症状：
  - 限制并发、加 `sleep` / `setTimeout` 延时、降低轮询或广播频率，却没有消除底层的浪费；
  - 新增重试循环，掩盖本应修正的逻辑错误；
  - 新增特殊判断（`if (x === 某个特殊值) return`），只绕开了出错的那一个用例；
  - 新增标志位或缓存，用来绕开混乱的数据流，而不是理顺数据流。
- 边界条件：空值、空集合、超大输入、重复调用、首次运行、升级迁移后的旧数据。
- 改动有没有改变原有行为、破坏其他调用方？

## 2. 数据一致性与失败路径

- 多步写入是否放在同一个事务（或 Savepoint）里？中途失败会不会留下半成品数据？
- 有没有「先删除旧数据、再执行耗时操作或网络请求」的写法？失败或取消时，旧数据是否已经丢失？
- 取消、超时、断网、进程被杀之后，系统能否恢复到一致状态？下次运行时会不会重复处理或漏掉数据？
- 操作是否幂等？重复执行一次会不会产生重复记录？
- 缓存、索引、账本类数据和主数据之间，会不会在某个时刻不一致？由谁负责修正？
- 数据格式或数据库结构有变化时，是否有迁移方案，旧数据能否兼容？

## 3. 并发与时序

- 是否存在竞态：两个流程同时读写同一份数据、同一个文件、同一个哈希或同一个状态？
- 锁、槽位、信号量是否在所有路径（包括异常、超时、取消）上都能释放？
- 有没有持有锁的同时执行网络请求、`sleep` 或其他长耗时操作？
- 后台任务和前台操作会不会互相抢资源，或者重复执行同一件事？
- 异步回调到达时，它依赖的状态是否可能已经被修改（过期数据、版本号检查）？

## 4. 性能与资源

- 循环里有没有逐条发出 HTTP、IPC 或数据库请求？能否合并为批量操作？
- 有没有 N+1 查询、同一份数据重复查询、同一个文件重复读取和解析？
- 算法复杂度：有没有在循环里调用 `find` / `filter` / `includes`，形成 O(N²)？能否改用 Map 或 Set 索引？
- 查询时有没有读取不需要的大字段（向量、BLOB、正文）？
- 有没有在筛选之前就对全部数据做反序列化或对象映射？
- 长时间的同步计算会不会阻塞主线程或 UI 线程？是否按时间片让出事件循环，或者移到 Worker？
- 内存：缓存或 Map 是否只增不减？大对象在用完后是否及时释放引用？
- 数据规模放大 10 倍、100 倍后，耗时和内存会怎样增长？

## 5. 错误处理与安全

- 有没有捕获异常后静默忽略？错误是否被记录，并且以合适的方式反馈给调用方或用户？
- 错误信息里有没有泄露密钥、令牌、个人数据或完整文件路径？
- 用户输入、文件内容、网络数据在进入 SQL、命令行、文件路径或 HTML 之前，是否经过参数化或校验？
- 密钥、凭证是否写死在代码里，或者被写进日志？
- 权限和访问控制：一个用户能否访问或修改另一个用户的数据？

## 6. 范围控制与可维护性

- 改动是否超出了任务需要？有没有顺手做的无关重构、新增依赖、新增抽象层？
- 有没有残留的调试代码、注释掉的旧代码、TODO 占位、未使用的函数和导入？
- 是否遵循项目现有的命名、目录结构、错误处理方式？是否违反项目规则（例如单文件行数上限、禁止的依赖）？
- 改动是否只修了一边：桌面端改了移动端没改，写路径改了读路径没改，主流程改了重试流程没改？
- 半年后别人读到这段代码，能不能理解它为什么这样写？不直观的地方是否有注释说明原因？
- 代码里的注释和文档，是否与实际行为一致？

## 7. 测试与可验证性

- 测试、类型检查、lint 和构建是否真的运行过并且通过？以你亲自运行的结果为准。
- 修复的 Bug 有没有对应的回归测试？测试是否真的覆盖了出问题的路径，而不只是覆盖正常路径？
- 测试有没有被修改、跳过或删除，以便让它们「通过」？
- 哪些场景只能在真实环境中验证（真机、大数据量、弱网、多设备同步）？在报告中列出来，交给用户测试。

## 输出

按上面 7 类列出发现的问题。每条写清：

- 位置：文件与行号；
- 现象：现在会发生什么；
- 为什么是问题：对应的正确性、一致性、并发、性能或安全风险；
- 建议怎么改。

没有问题的类别写「无」，不要硬凑。最后单列「未验证的场景」，说明哪些只能在真实环境中确认。
